# SchGen — design rationale

The decisions that shaped schgen, with the alternatives they ruled out. Read this before changing the architecture or arguing about it.

## 1. YAML, not a Python DSL or a GUI

KiCad's schematic editor is mouse-driven and stateful. Hand-edited `.kicad_sch` files are not reviewable in a code-review tool — moves and refactors produce noisy diffs across thousands of `(at x y)` tuples. The two common alternatives are:

- **Python DSL** (skidl / SchemDraw / circuit-generators). Components and nets become Python objects; you write code to wire them. Pros: full programming language. Cons: encourages clever abstractions (`def make_decoupling_cluster(...)`) that bury what's actually on the schematic, and review becomes "trust the helper" instead of "read the wiring." See [no-circuit-DSL memory in the source project] — the project explicitly rejected DSL wrappers.
- **GUI authoring**. eeschema works. But it's not reviewable, not regeneratable, and not scriptable.

**YAML wins because it's declarative and reviewable.** Every component, every pin, every net is explicit text. A PR diff shows exactly which pin moved between which nets. No helper code stands between the YAML and the schematic. The cost is verbosity — a 500-pin SoC is a long YAML block — but the value of having the wiring fully in source-control text outweighs that cost on the kind of boards schgen targets (multi-IC mixed-signal, where reviewability of net assignments is more important than authoring speed).

## 2. Pin → net attribution, not separate `nets:` lists

Most circuit DSLs let you declare nets separately and then attach pins to them:

```python
gnd = Net('GND')
gnd += U1[10], U1[20], C1[2], C2[2], ...
```

schgen rejects this in favor of **per-pin attribution on the component**:

```yaml
- ref: U1
  pins: { 10: GND, 20: GND, ... }
- ref: C1
  pins: { 1: VBUS, 2: GND }
```

Nets emerge from the union of pin attributions. Why:

- **Locality.** When you read U1, you see which net every pin goes to without scrolling to another section.
- **No "where is this net defined" question.** The net's existence is whatever pin attributions reference it. Move a pin off a net by editing the pin; the net cleans itself up.
- **Refactor safety.** Renaming a net is a global text rename, not a search-for-the-declaration-then-update-references operation.
- **No declared-but-unused nets.** The validator can warn when `power_nets:` lists a name nothing references; the same trick doesn't work cleanly with a separate `nets:` block where the declaration is the point.

The downside is that there's no single place to ask "what's on net X." The validator and the placer build that index on the fly. Worth it.

## 3. Implicit NC for unattributed pins

By default, any symbol pin not listed in a component's `pins:` block becomes a no-connect marker. The alternative is requiring every pin to be explicit. The implicit form was chosen because:

- A 600-ball BGA where 200 pins are NCs (test/factory pins, reserved, unused functions) would double the YAML if every NC had to be written.
- ERC will catch genuinely-missing connections via the pin-electrical-type rules — `power_in` pin with no driver throws `power_pin_not_driven` regardless of whether you wrote `NC` or omitted it.
- Explicit `NC` is still available (`pin_id: NC`) for the rare case where you want to make the no-connect intentional and reviewable.

## 4. Source-verbatim symbol embedding

When schgen emits a `.kicad_sch`, every symbol it instantiates is embedded inline as a `(lib_symbols)` block — a complete copy of the symbol definition, not a reference to an external library. This costs ~50–500 bytes per unique symbol instance.

The alternative is the conventional KiCad pattern: symbol stays in the library; the schematic just references `(symbol "Lib:Name")`. That breaks reviewably and reproducibly:

- The schematic depends on whichever revision of the library happens to be installed when you open it. Two engineers see different things.
- Library updates can silently retag pins or break footprint mappings on existing boards.
- `kicad-cli sch erc` raises `lib_symbol_mismatch` whenever the in-schematic copy drifts from the library — and any change to the library is a drift.

**Embedding gets us hermetic builds.** The schematic is what it claims to be. To compensate for losing the "live library update" flow, schgen always re-reads the YAML's listed libraries on every build, so refreshing a symbol is `schgen build`-and-done.

The `.kicad_pro` generated by schgen pre-silences `lib_symbol_mismatch` and `lib_footprint_mismatch` because they would be permanent false positives under the embedding scheme.

## 5. Net naming as the cluster signal

The placer needs a rule for "this cap belongs near that IC pin." Pattern-matching on values (`100nF` → bypass) or footprints (`0805 + small value` → bypass) would over-fire (not every 100nF is a bypass) or under-fire (sometimes a tantalum is the bypass).

schgen uses **net naming as the cluster signal**: a 2-pin passive whose net has exactly one non-passive endpoint goes adjacent to that endpoint on both the schematic and the PCB. To get strong clustering, author the YAML with **dedicated stub nets**:

- `VCC_3V3_U_SOC_A1` (cap + U_SOC.A1 only) — proximity fires, cap glues to U_SOC.A1.
- Just `VCC_3V3` (shared with 50 sinks) — proximity does not fire, cap floats with the rest of the rail.

This makes the *author* the source of intent. The placer does no heuristic guessing; the YAML net naming says exactly which IC pin each bypass belongs to. The cost is more YAML net names; the value is deterministic placement that doesn't surprise the user.

`host: <refdes>.<pin>` is an explicit override for the rare cases where the net-naming convention can't capture the intent (e.g. a cap shared between two ICs where you want it next to the second).

## 6. Sheets pre-assigned in YAML; placer fills in positions

Every component declares which sheet it lives on. The placer only chooses the position within that sheet; it never moves components between sheets.

The alternative (let the placer auto-partition into sheets based on connectivity) would be:

- Non-deterministic across builds (graph-cut algorithms make different choices on equivalent inputs).
- Confusing during review (a PR that doesn't touch sheet assignments could re-shuffle them).
- Bad at honoring real-world groupings ("power", "USB", "memory") that aren't purely connectivity-driven.

User intent for grouping is more important than algorithmic optimality. The placer's job is layout, not architecture.

## 7. Hierarchical sheets are flat at the YAML level

KiCad supports nested hierarchical sheets (sheet inside sheet inside sheet). schgen produces a one-level hierarchy: root sheet + N sub-sheets, no deeper. Sub-sheets connect to the root via hierarchical labels (template `ports:`) or via global labels (`power_nets:` or singleton nets referenced from multiple sheets).

This was chosen because:

- Two-level hierarchies are unambiguous and trivially printable on a single A3 sheet of root + thumbnails.
- Three-level hierarchies (root → power-domain → power-domain-sub) buy little real-world clarity and make navigation harder.
- Boards larger than two-level can use `includes:` to split the YAML across files while keeping the schematic flat.

If a real need ever surfaces for true nesting, the YAML schema accommodates it: a template's `components:` block could become `sheets:` with another nested `root.instantiate:`. The current implementation enforces flat-only at the loader level.

## 8. PCB placement is "clusters by sheet," not a real layout

`schgen build` emits a `.kicad_pcb` where each sheet's footprints sit in a labeled rectangular region. No routing, no length matching, no controlled-impedance lanes — those are user work in pcbnew.

The placer outputs are deliberately the starting state, not the finished layout. Reasons:

- Real PCB layout depends on board outline, stackup, edge connectors, and high-speed signal constraints that the YAML doesn't (and shouldn't) model.
- Cluster-by-sheet matches the schematic's logical groupings, so when the user opens pcbnew they see the same chunks they wrote in the YAML.
- The user is the source of truth on placement — schgen owns the "what's on the board"; the user owns "where it goes."

## 9. `dotnet` over Python (the language choice)

The original prototype was Python. It moved to C# / .NET 9 because:

- KiCad's `.kicad_sym` / `.kicad_sch` / `.kicad_pcb` files are deeply nested S-expressions. A real type system (records + pattern matching) made the emitter dramatically clearer than the equivalent Python.
- Performance — the placer's cap-proximity + collision-fanout pass over a 600-component board went from ~12 s in Python to ~150 ms in C#.
- xUnit + the .NET tool ecosystem (`dotnet pack`, `dotnet tool install`) gave a clean distribution story for free.

The .NET runtime adds an install dependency, but `dotnet tool install --global` makes that one-time and self-contained.

## 10. Two-test-per-rule design

The xUnit suite (87 tests today) has a pattern: every emitter rule or placement rule has at least two tests — one for the rule firing, one for the rule NOT firing. E.g. cap-proximity has tests for both "cap with single host → adjacent" and "cap with shared host → not adjacent." This catches the worst class of bug — a rule that's been silently disabled by a refactor — without doing differential snapshot testing (brittle on layout output).

Regression policy: any new validator diagnostic, emitter behavior, or placement heuristic ships with at least one positive and one negative test.

## What schgen explicitly does not do

| Not in scope | Why |
|---|---|
| Routing | Real PCB routing is a user / specialized-tool job. The emitted `.kicad_pcb` is unrouted by design. |
| Differential pair declaration | Net classes + diff pairs are layout concerns; declare them in pcbnem against the schgen-emitted board. |
| BOM emission | `kicad-cli sch export bom` already does this against the emitted `.kicad_sch`. Don't reimplement. |
| ERC | KiCad's `kicad-cli sch erc` is the authoritative ERC runner. schgen only does *YAML-level* validation (symbol/footprint/pin resolvable, refdes unique, etc.). |
| Symbol authoring | Use KiCad's symbol editor (`kicad-cli sym new` / eeschema's symbol editor). schgen *reads* `.kicad_sym` files but doesn't generate them. |
| Footprint authoring | Same — KiCad's footprint editor. schgen reads `.kicad_mod` files via `.pretty` directories. |
| 3D model placement | KiCad reads 3D bindings from the footprint definitions; schgen passes them through unmodified. |
| Auto-routing | Out of scope. Use freerouting or KiCad's built-in router against the emitted `.kicad_pcb`. |

## Version compatibility

- KiCad target: **10.0**. The emitted S-expression dialect uses 10.0 conventions (UUIDs, embedded `lib_symbols`, page-format strings). Older KiCad versions will partially open the output but with degradation; 11.0+ is untested.
- Runtime: **.NET 9.0**. No older runtime is supported.
- OS: tested on Linux. macOS and Windows should work (no platform-specific code) but aren't part of CI.
